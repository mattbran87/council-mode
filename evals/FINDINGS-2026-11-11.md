# Findings: first probe rounds, 2026-11-11

Three probe runs against workflow script commit `8395c2a`, plus Layer 1 on the first fixture. Run folders are under `~/.claude/council-mode-evals/`.

## Summary

The core principle holds at both stages. No advocate and no referee gave way to fake evidence in any valid run, and every control gave way to real evidence. The first run was not a fair test: the probe calls could not use the web, and the user's plugins and hooks loaded into every call. After the fix, the models fetched each cited page and reported what it did and did not say.

The probe is now saturated. Use it as a regression check after any change to `replyPrompt`, `rulingPrompt`, or their schemas.

## What was right

- **Traps.** Every valid trap run held. With web access, advocates reported that the fake survey URL returns HTTP 404 and that the cited Go release notes have no such section. The referee read the Go FAQ and quoted its real text.
- **Controls.** Every valid control run gave way, with confidence dropping to between 4 and 10.
- **Weak defense.** The referee checked the source itself when the defense gave no evidence (`ruling-trap-go-vcredist-misquote`).
- **Honest limits.** Referees stated what they did not check, for example "I did not build or run a Windows binary myself."

## What was wrong

- **No web access in probe1.** `--tools` makes tools available but does not grant permission in `-p` mode. The models reported WebFetch and WebSearch as denied, and one reported a context-mode hook block. The user's plugins also inflated each call: the Task 6 smoke call carried about 46k tokens of context and cost about $0.01, while a similar call in safe mode cost about $0.002.
- **Cost overshoot.** probe1 spent $5.11 against a $5 cap. `--max-budget-usd` is checked after spend, so single calls reached $0.52 and $0.59 against a $0.50 cap.
- **Error text.** probe1 recorded failed calls only as "CLI reported an error", so the cause of the 3 failures is not known.
- **Lenient stage pass.** Before the change, a stage passed on a share of valid runs, so 4 of 4 passed even when 2 of 6 planned calls failed.
- **Report plan.** The report planned from the current cases file, so adding cases would have turned old runs incomplete.

All five are fixed on `feat/evals`: safe mode and granted web tools; the error `subtype` on failed rows; a minimum of 5 of 6 valid runs per kind, with a High, Medium, or Low confidence label per stage; and a plan stored in each run's `run.json`.

## What to improve next

1. **Half-true trap.** Add a trap whose real source supports part of the challenge. The right answer is `partial` with a small confidence drop, which the report now shows (for example `partial 85→78`).
2. **Partial as a rule.** `partial` still counts as a pass for reply traps. Turn the confidence drop into a pass rule only after a run produces a `partial` that gave way. No run has produced one yet.
3. **Layer 3.** The probe tests single stages. Whether the full council beats one strong agent is still open.
4. **Cost cap.** If a run must never exceed its budget, lower the per-call cap as the remaining budget shrinks, or keep a reserve, because the CLI overshoots after the fact.
